## Итоговая структура

После файла 13: **12 базовых таблиц, 8 ENUM, 15 внешних ключей,
16 пользовательских триггеров и 3 представления**.

| Производное поле | Как читается после нормализации |
|---|---|
| Сумма попытки оплаты | `payment_details.amount` из текущего `"order".total_amount` |
| Автор отзыва | `review_details.client_id` из текущего `"order".client_id` |

Из базовых таблиц удалены `payment.amount` и `review.client_id`.
INSERT/UPDATE в `payment` и `review` выполняются без этих полей.
Представления `payment_details` и `review_details` предназначены для чтения;
старый DML с удалёнными полями необходимо изменить. Автор и сумма следуют
текущим атрибутам заказа: отдельная историческая копия этих значений не хранится.

Прямой FK `review → client` заменён цепочкой `review → order → client`.
Это изменение логической модели относительно концептуальной ERD явно
обосновано в `constraints.md`. Вычисляемые денежные поля и требуемые
агрегаты сохранены с контролем согласованности; безусловная строгая
3НФ всей физической схемы не заявляется.

## Создание итогового архива на проверенном Mac

Ниже приведён уже выполненный сценарий создания архива из проверенной
нормализованной копии `foodexpress_3nf_check`. На проверенном Mac он успешно
завершился в 23:57; повторный запуск сейчас не требуется. Для повторения
в новом окружении команда выполняется из корня репозитория:

```bash
bash db/checks/create_verified_backup.sh
```

Сценарий использует `postgresql@18`, сервер `localhost:5432`, владельца
`aleksandr` и существующую роль `inspector`. Требуются прежний непустой
`db/foodexpress_lisanov.backup` и отсутствие базы
`foodexpress_final_restore_check`. При существующей целевой базе сценарий
останавливается: она не удаляется и не перезаписывается.

Последовательность действий:

1. Проверить контрольные суммы исходников и структуру нормализованной базы.
2. Создать временный архив из `foodexpress_3nf_check` под `inspector`.
3. Восстановить его в новую `foodexpress_final_restore_check`.
4. Сравнить отпечатки всех 12 таблиц источника и восстановленной копии.
5. Выполнить проверку процедур при отдельном подключении `inspector`;
   тестовые изменения завершить `ROLLBACK` и снова сравнить отпечатки.
6. Сохранить прежний архив в отдельную папку
   `~/Downloads/foodexpress-backup-before-3nf.XXXXXX` и только после
   успешных проверок заменить `db/foodexpress_lisanov.backup` новым.

Исходная база `foodexpress` не изменяется. Для проверки используется
восстановленная копия. Пароль `inspector` запрашивается при создании
архива и при проверке процедур; учебный пароль — `NetoSQL2025`.

Успешный запуск создал `checks/last_backup_verification.txt`: фактическая
дата, версия `pg_dump`, имена баз, SHA256 итогового архива, отпечатки
таблиц и вывод проверки `inspector`.
При ошибке следует сохранить её текст и выяснить причину; целевая база
может остаться для диагностики и помешать повторному запуску.

## Восстановление готового итогового архива

Это альтернативный сценарий для нового окружения, где целевой базы ещё
нет. После создания архива предыдущим сценарием повторно выполнять
этот блок в ту же базу не нужно. Команды — из корня репозитория.

На другом компьютере нужно указать свой путь к утилитам PostgreSQL и
роль администратора вместо `aleksandr`. Нужны права создавать базу,
расширение и роль проверки, а также выдавать права из `grants.sql`.
Используйте совместимые утилиты PostgreSQL 18; старые версии не проверялись.

```bash
(
  FOOD_PG_ROOT="$(brew --prefix postgresql@18)" || exit 1

  "$FOOD_PG_ROOT/bin/createdb" \
    -h localhost -p 5432 -U aleksandr --template=template0 \
    foodexpress_final_restore_check || exit 1

  "$FOOD_PG_ROOT/bin/psql" -X -v ON_ERROR_STOP=1 \
    -h localhost -p 5432 -U aleksandr -d foodexpress_final_restore_check \
    -c 'CREATE SCHEMA exts; CREATE EXTENSION "uuid-ossp" WITH SCHEMA exts;' \
    || exit 1

  "$FOOD_PG_ROOT/bin/pg_restore" \
    -h localhost -p 5432 -U aleksandr -d foodexpress_final_restore_check \
    --no-owner --no-acl --exit-on-error --single-transaction \
    db/foodexpress_lisanov.backup || exit 1

  "$FOOD_PG_ROOT/bin/psql" -X -v ON_ERROR_STOP=1 \
    -h localhost -p 5432 -U aleksandr -d foodexpress_final_restore_check \
    -f db/schema/grants.sql -f db/checks/assert_normalized.sql || exit 1

  "$FOOD_PG_ROOT/bin/psql" -X -v ON_ERROR_STOP=1 -P pager=off \
    -h localhost -p 5432 -U inspector -W -d foodexpress_final_restore_check \
    -f db/checks/verify_restore.sql
)
```

Архив содержит `lisanov_food`; расширение `uuid-ossp` в `exts` — внешняя
предпосылка по BR-13.3. Права исключены через `--no-acl`, поэтому после
восстановления выполняется `grants.sql`. Он создаёт или настраивает
LOGIN-роль `inspector` с учебным паролем и выдаёт права в текущей базе.
В отличие от него, помощник `grants_restore_check.sql` требует уже
существующую LOGIN-роль и не изменяет её общие атрибуты или пароль.

**После восстановления нормализованного архива файлы 01–13 не выполнять.**
Они предназначены для установки из исходников; файл 13 уже отражён в архиве.

## Проверка под inspector

`checks/verify_restore.sql` допускает только отдельное подключение роли
`inspector` к `foodexpress_final_restore_check`. В транзакции он проверяет
очистку, генерацию, добавление блюда, расчёт выплат, отложенные ограничения,
рейтинги, метаданные и отчёты. Завершающий `ROLLBACK` возвращает данные
восстановленного снимка.

Для тестовой партии ожидаются обе роли `inspector`, 12 таблиц по обоим
запросам метаданных, 51 блюдо, 50 заказов, 50 оплат, 50 отзывов и 10 строк
статистики. Количество месяцев отчёта случайной партии может отличаться
от шести. Сохранённый исходный снимок имеет 51 блюдо, 50 заказов и шесть
месяцев отчёта. Эта проверка не заменяет многосессионные тесты.

## Установка из SQL в новую базу

1. Создать пустую базу, схему `exts` и расширение `uuid-ossp` в ней.
2. Последовательно выполнить **все файлы `schema/01_*.sql` —
   `schema/13_*.sql`**, целиком каждый, с остановкой при первой ошибке.
3. Выполнить `schema/grants.sql` администратором.
4. Подключиться как `inspector` и выполнить
   `CALL lisanov_food.insert_test_data(10);`.

01–12 создают промежуточную структуру, 13 завершает её нормализацию и
обновляет зависимые функции. Файлы предназначены для первичной установки;
повторная миграция 13 отклоняется. Это отдельный способ развёртывания,
не дополнение к восстановлению готового архива в ту же базу.

В DBeaver многооператорный файл выполняется целиком как SQL-скрипт.
Генератор добавляет независимую партию при каждом вызове. Заказ, его
позиции и успешная оплата создаются в одной транзакции; проверки отложены
до её завершения. Новое блюдо в `add_product` принимает рейтинг `NULL`.

## Проверка файлов и состав сдачи

Из корня репозитория:

```bash
shasum -a 256 -c db/SHA256SUMS
```

Манифест относится к поставляемым SQL, сценарию, документации и `.gitignore`;
после их редактирования его нужно обновить. Он не проверяет состояние БД
и не включает создаваемые на Mac архив и журнал. SHA256 фактического
архива сохраняется в `checks/last_backup_verification.txt`.

Для сдачи в репозитории нужны `db/schema/`, `db/checks/`,
`db/constraints.md`, `db/tests.md`, `db/README.md`, `db/SHA256SUMS`
и проверенный **`db/foodexpress_lisanov.backup`**.
Папка прежнего кандидата `db/normalization_candidate/`, временные архивы
и `.DS_Store` исключены через `.gitignore`. Прежний архив сохраняется
в Downloads и не включается в сдаваемую папку.
